Effective Diameter – Forward Slip (Ekelund)

PyRoll GUI  |  Date: October 2026

1. Introduction

During rolling, the material at the neutral point moves slightly faster than the geometric roll surface speed implied by the working diameter alone — an effect known as forward slip. Converting a simulated strip velocity into a real motor/roll RPM without accounting for this effect systematically understates the true rotational speed required.

PyRoll WebGUI computes an Effective Diameter and the corresponding Forward Slip percentage for every TwoRollPass/ThreeRollPass stand, shown in the Results table directly under Working Diameter, and offers an optional RPM Basis switch in Pass Design to use this corrected diameter for RPM calculations.

2. Ekelund's Formula

The classical, empirically validated method by Ekelund derives the forward slip from the bite geometry and the friction coefficient:

\[ \alpha_n = \sqrt{\frac{\Delta h}{R}} - \frac{\mu}{2} \] \[ \text{FWS} = \frac{R \cdot \alpha_n^2}{2 \cdot h_{1,\text{eq}}} \] \[ D_{\text{eff}} = D_{\text{work}} \cdot (1 + \text{FWS}) \]
SymbolMeaningSource in PyRoll WebGUI
\(R\)Working radiusunit.roll.working_radius (same value shown as "Working Diameter" / 2)
\(\Delta h\)Equivalent height reductionin_profile.equivalent_height − out_profile.equivalent_height
\(h_{1,\text{eq}}\)Equivalent outgoing heightout_profile.equivalent_height
\(\mu\)Coulomb friction coefficientunit.coulomb_friction_coefficient — the per-pass value entered in Pass Design, same value used for roll force/torque/spread

equivalent_height is PyRolL Core's groove-agnostic \(h_{\text{eq}} = \sqrt{A \cdot h / w}\) hook (overridden by the Lendl equivalent-height method for actual roll-pass profiles — see the Working Diameter method page), so this calculation works for any groove type, not just flat/box passes. If \(\Delta h \le 0\) (no real reduction) the result is left undefined and the Results table shows "—".

3. Why Ekelund, Not PyRolL's Built-In Neutral-Angle Model

PyRolL Core ships a tension-aware neutral-angle hook (Lippmann-Mahrenholz, pyroll.lippmann_mahrenholz_force_torque) that is already active in the app for roll force/torque calculations. It was evaluated as an alternative source for forward slip before this feature was implemented.

Cross-checking PyRolL's relative_neutral_angle function directly (not an approximation) against a reference case with 35.2 % reduction and \(\mu = 0.343\) gave:

ModelForward Slip
PyRolL (Lippmann-Mahrenholz), zero interstand tension≈ 0.45 %
Ekelund (same input data)≈ 4.65 %

A roughly 10× gap. The root cause: PyRolL computes \(\text{neutral\_angle} = \text{entry\_angle} \times \text{relative\_neutral\_angle}\), where relative_neutral_angle came out to only ≈ 0.32 in this example — the model scales the angle down by a fraction rather than computing it directly, as Ekelund's formula does. This is not a bug; it is an inherent property of how this particular PyRolL plugin formulates the neutral point. But for a figure meant to be compared directly against real nameplate/drive RPM data, we chose the formula with the longer, better-documented empirical track record.

Note: PyRolL's neutral-angle model notably does not use the friction coefficient directly — it derives the neutral point from draught, equivalent height, and (if present) interstand tension instead. It may still be the more appropriate model for tension-aware force/torque corrections, which is unaffected by this change — only forward slip/RPM uses Ekelund's formula.

4. The "RPM Basis" Switch

Pass Design offers a per-sequence RPM Basis selector (next to Disk Element Count):

OptionEffect
Working Diameter (default)Roll RPM / Motor RPM computed from the geometric working diameter, unchanged from previous versions.
Effective Diameter (Ekelund)Roll RPM / Motor RPM computed from the forward-slip-corrected effective diameter above.
Scope: the switch only applies to velocity-defined stands (Standard, Forward, and Backward Solve). Finishing Block sub-passes keep their prescribed motor RPM as the authoritative input regardless of this setting — that RPM is a hard physical input (from motor RPM / gear ratio), not something derived from simulated velocity that forward slip could correct.
Does not affect simulated rolling velocity: PyRolL's own mass-conservation solve always uses the working diameter internally to relate velocity and rotational frequency. This switch only changes how an already-simulated, unchanged velocity is converted into a displayed RPM figure — it does not feed back into profile dimensions, roll force, torque, power, or temperature results.

The default remains Working Diameter — nothing changes for existing projects unless the switch is explicitly changed. We recommend validating Effective Diameter against real measured motor RPM for your own mill before relying on it operationally, since forward slip depends strongly on friction, reduction, and contact geometry that vary between mills.
